### H1–H2. Topología, refs y protección

- **T-A preferida.** Dos commits raíz diferentes, cada uno con cero padres y con árbol de génesis propio. Prepararlos desde contenido nuevo en un espacio de trabajo aislado de YU3DOH. Para la futura solicitud, elegir un operador y un método específico. La vía Git CLI con creación de raíces sin padre es viable según la semántica documentada de Git. En las acciones del conector, `create_commit` requiere `parent_sha` y `create_branch` parte de una referencia o SHA existente. La API Git Database de GitHub tiene un contrato distinto y admite un commit raíz sin padres, pero rechaza inicializar una referencia por esa API si el repositorio está vacío. La vía completa de G2-B y sus protecciones siguen `NOT VERIFIED`. [Git — commit-tree](https://git-scm.com/docs/git-commit-tree) · [GitHub Docs — commits](https://docs.github.com/en/rest/git/commits#create-a-commit) · [GitHub Docs — refs](https://docs.github.com/en/rest/git/refs#create-a-reference)
- **Prueba a exigir en el gate futuro.** Fijar nombre e ID del repositorio, visibilidad, rama por defecto `main`, refs exactas esperadas, parentage, digest y modo de archivos, autor/committer aprobados y reglas efectivas. Para T-A, inspeccionar el grafo completo por SHAs con ambos objetos disponibles, una única raíz por tip, raíces distintas y ausencia de ancestro común con `git merge-base`; distinguir el resultado esperado de un error de acceso o historia incompleta. Inventariar además las refs y superficies publicadas que puedan revelar contenido fuera de los dos árboles. Si el plan requiere simultaneidad de dos refs, exigir garantía de actualización conjunta de la ruta seleccionada o un procedimiento explícito para el caso de primera rama publicada y segunda rechazada. Tras un resultado parcial, contrastar refs contra los valores aprobados, detener importación y remitir la recuperación al Owner. [Git — merge-base](https://git-scm.com/docs/git-merge-base) · [Git — push](https://git-scm.com/docs/git-push)
- **T-B solo mediante decisión explícita.** El único padre común admisible sería una génesis neutral del propio maestro, exactamente identificada y aprobada para permanecer visible desde ambas ramas. Sustituir el árbol de una rama conserva los ancestros. Excluir padres provenientes de YU3DOH o con material exclusivo de la otra rama. Documentar el ancestro común esperado y la política de rutas aun si T-A siguiera siendo preferible.
- **Protección y operación.** Definir reglas efectivas por ref para creación, actualización, borrado y force-push, más los actores con bypass y su duración. Acreditar que los permisos de actualización no habilitan borrado ni reescritura por una excepción compartida. Documentar el orden de arranque de reglas y cualquier ventana entre creación y protección, el operador único durante ese intervalo y el readback. Los cambios posteriores requieren ramas candidatas de su propio linaje, controles de árbol/delta y destino, y una ruta practicable para actualizar ambas refs con las reglas activas. Historial lineal elimina commits de merge, pero una publicación por squash, rebase, cherry-pick o copia puede mantener el grafo lineal y cruzar contenido. El adaptador congelado exige un valor anterior explícito y avance fast-forward en las líneas 11–18. Una lectura previa seguida de actualización sin condición, un `force=false` genérico y un HEAD estable observado no demuestran CAS. Mantener `NOT VERIFIED` para la ruta efectiva de actualización protegida, con un criterio de STOP si la configuración la impide. [GitHub Docs — reglas y bypasses](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) · [GitHub Docs — acumulación de reglas](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
